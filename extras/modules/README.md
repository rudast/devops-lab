# Модули Terraform (черновик занятия — отложено)

> **Черновик.** Сейчас занятие 12 — «Terraform в повседневной работе», см. [lesson12/README.md](../../lesson12/README.md). Модуль `vm` лежит рядом: `extras/modules/modules/vm`; пути `lesson12/…` в тексте ниже читайте как `extras/modules/…`.

На занятии 11 вся инфраструктура приложения жила в одном `main.tf`: сеть, firewall, ключ, ВМ с cloud-init, публичный IP. Для одной ВМ этого достаточно. Но как только серверов становится несколько, а облако общее на всю группу, нужны три вещи:

1. **Модуль** — описать «сервер» один раз и вызывать его как функцию.
2. **`for_each`** — сервер становится строкой в карте, а не копией блока.
3. **Проверки входов внутри модуля** — всё, что на занятии 11 мы писали в `main.tf` руками (минимальный тип ВМ, минимальный диск, зона по хэшу), переезжает внутрь модуля и работает для любого, кто его вызывает.

```
                    ┌──────────── practice/ (корневой модуль) ─────────────┐
var.servers = {     │  module "firewall" ──▶ ./firewall         (часть 6)   │
  web-1 = {}  ──▶   │  module "web" (for_each) ──▶ ../modules/vm             │
}                   │        │  сам выбирает: образ · тип · диск · зону      │
                    └────────┼──────────────────────────────────────────────┘
                             ▼
                 одна ВМ на команду в общем проекте cloud.ru
```

## Квоты: почему работаем в парах

В общем проекте курса лимит — **15 ВМ, 30 vCPU, 60 ГБ RAM, 1200 ГБ диска** на всю группу (30 человек). Поэтому:

- работаем **командами по 2** (если нечётно — по 3): **одна ВМ на команду**, 14 команд + ВМ преподавателя = 15;
- тип ВМ — только минимальный **s7n.medium.2** (1 vCPU / 2 ГБ): 15 ВМ × 1 vCPU = 15 из 30;
- диск — **минимум образа**, больше 20 ГБ нельзя;
- зону модуль выбирает сам: «случайную» по хэшу имени, и только ту, где тип s7n.medium.2 сейчас есть. ВМ команд расходятся по разным зонам, и `apply` не падает из-за «распроданной» зоны.

На занятии 11 эти правила жили в `main.tf` практики. Теперь они зашиты в модуль `modules/vm` проверками `validation`: нарушить квоту случайно не получится, `terraform plan` остановится с понятной ошибкой ещё до обращения к облаку.

### Часть 1. Модуль: читаем и вызываем (20 мин)

Модуль — это просто папка с `.tf`-файлами. У него есть **входы** (`variable`), **выходы** (`output`) и ресурсы внутри.

```bash
cd lesson12
cat modules/vm/variables.tf     # входы: name, subnet_id, key_pair… и flavor, disk_size с проверками
cat modules/vm/main.tf          # ВМ + публичный IP (EIP) + выбор зоны — знакомый код занятия 11
cat modules/vm/outputs.tf       # выходы: id, name, zone, flavor, disk_size, private_ip, public_ip, url
```

Код внутри вам знаком по занятию 11. Найдите в `modules/vm/main.tf` и обсудите в паре, что изменилось:

| Что | Где | Зачем |
|---|---|---|
| `data "sbercloud_compute_flavors" "zone"` с `for_each` по зонам | начало файла | список типов ВМ в **каждой** зоне |
| `local.zones` | `locals` | только зоны, где наш тип есть |
| `local.hash` и `local.auto_zone` | `locals` | «случайная», но стабильная зона: хэш имени → номер зоны |
| `ignore_changes = [availability_zone, image_id]` | `lifecycle` у ВМ | если список зон или образ изменятся, ВМ **не** пересоздаётся |
| `count = var.public_ip ? 1 : 0` | у EIP | ресурс «по условию»: одна копия или ни одной |

> Модуль не знает, откуда взялись подсеть и ключ: их передаёт вызывающий код. А вот образ, тип, диск и зону он выбирает сам — это и есть разница с занятием 11, где всё это лежало в корневом `main.tf`. Вызов получается коротким, а квоту не нарушить.

Теперь вызываем модуль:

```bash
cd practice
export SBC_ACCESS_KEY="…"  SBC_SECRET_KEY="…"      # ключи от преподавателя
cp terraform.tfvars.example terraform.tfvars        # впишите prefix команды: ivanov-petrov
grep -n TODO main.tf                                # три TODO в блоке module "web"
```

Замените три `TODO` в `main.tf`:

| TODO | Что подставить | Подсказка |
|---|---|---|
| `source` | путь к папке модуля | относительно папки `practice` |
| `subnet_id` | ID общей подсети | её уже читает `data "sbercloud_vpc_subnet" "course"` выше |
| `key_pair` | **имя** ключа | ресурс `sbercloud_kps_keypair.key` выше |

```bash
terraform init          # скачает провайдер и «подключит» модуль: "- web in ../modules/vm"
terraform plan          # Plan: 7 to add. Найдите в плане availability_zone и system_disk_size
terraform apply
terraform output        # zone, flavor = s7n.medium.2, disk_size — минимум образа
curl $(terraform output -raw url)        # «Я — <prefix>-web-1» (через 1–2 мин)
terraform state list                     # module.web.sbercloud_compute_instance.this — адрес ресурса внутри модуля
```

Сравните `zone` с соседними командами: у разных имён — скорее всего, разные зоны.

### Часть 2. Ломаем входы: validation (10 мин)

Проверки в модуле срабатывают на `plan`, **до** обращения к облаку. Проверим.

**1. Чужой тип ВМ.** Добавьте в вызов модуля строку `flavor = "s7n.large.4"` и запустите `terraform plan`:

```
Error: Invalid value for variable
  В общем проекте курса разрешён только тип s7n.medium.2 …
```

**2. Большой диск.** Уберите `flavor`, добавьте `disk_size = 50` → `terraform plan` → ошибка про 20 ГБ. Посмотрите в `modules/vm/variables.tf`, как написана проверка и почему там `? :`, а не `||`.

Уберите `disk_size`: план снова должен стать `No changes`. Это те же правила, что на занятии 11 — только теперь они внутри модуля и действуют на каждого, кто его вызывает.

**3. Своя проверка.** Квота — одна ВМ на команду. Откройте `variables.tf`, найдите переменную `servers` и допишите `validation`: в карте не больше одного сервера (функция `length`). Проверьте — раскомментируйте в `terraform.tfvars` карту из двух серверов:

```bash
terraform plan      # Error: Квота: не больше одной ВМ на команду
```

Верните в `terraform.tfvars` **один** сервер: `servers = { "web-1" = {} }` (или закомментируйте карту — по умолчанию там и так один `web-1`).

<details><summary>Ответ</summary>

```hcl
validation {
  condition     = length(var.servers) <= 1
  error_message = "Квота: не больше одной ВМ на команду (15 ВМ на всю группу)."
}
```
</details>

### Часть 3. for_each и moved (15 мин)

Переменная `servers` — карта «имя сервера → настройки». Сейчас в ней один `web-1`, и больше квота не даст. Но код будет готов к любому числу серверов.

**1. Превращаем один вызов модуля в карту вызовов.** В `main.tf`, в блоке `module "web"`:

```hcl
module "web" {
  source   = "../modules/vm"
  for_each = var.servers                                  # ← добавить

  name      = "${var.prefix}-${each.key}"                 # ← было "${var.prefix}-web-1"
  disk_size = each.value.disk_size                        # ← добавить (null — минимум образа)
  ...
  user_data = templatefile("${path.module}/cloud-init.yaml.tftpl", {
    name = "${var.prefix}-${each.key}"                    # ← и здесь
  })
}
```

`each.key` — имя сервера из карты, `each.value` — его настройки. В `outputs.tf` **закомментируйте** выходы части 1: `module.web` теперь карта, у неё нет `.zone`. Свои выходы напишете в части 4.

**2. Смотрим план — и пугаемся.**

```bash
terraform plan
```

План хочет **удалить** `module.web` и создать `module.web["web-1"]`. Почему? У ресурса сменился **адрес** в state: был `module.web`, стал `module.web["web-1"]`. Terraform думает, что это разные серверы.

**3. Говорим Terraform, что это переезд.** Раскомментируйте в `main.tf` блок `moved`:

```hcl
moved {
  from = module.web
  to   = module.web["web-1"]
}
```

```bash
terraform plan      # web-1: "has moved to module.web["web-1"]" — 0 to add, 0 to destroy
terraform apply
```

**4. Только `plan`.** Добавьте в `terraform.tfvars` второй сервер — `plan` упадёт на вашей проверке из части 2. Временно закомментируйте `validation` и снова `plan`: план покажет `+` **только** для нового сервера, `web-1` не трогается. **Не применяйте!** Верните проверку и один сервер.

> **Почему не `count`?** С `count` серверы адресуются по номеру: `[0]`, `[1]`, `[2]`. Уберите из списка средний — номера «сдвинутся», и Terraform изменит не тот сервер, а настоящий последний удалит. У `for_each` адрес — имя (`["web-3"]`), оно не сдвигается. Правило: `count` — для «включить/выключить» (0 или 1, как EIP в модуле), `for_each` — для коллекций.

### Часть 4. Выходы через for (10 мин)

`module.web` теперь карта: `{ "web-1" = <выходы модуля> }`. Чтобы собрать из неё список или новую карту, нужно **for-выражение**:

```hcl
[for k, vm in module.web : vm.private_ip]               # список:  ["192.168.8.11"]
{ for k, vm in module.web : k => vm.private_ip }        # карта:   { "web-1" = "192.168.8.11" }
[for k, s in var.servers : k if s.disk_size != null]    # с фильтром if
```

Раскомментируйте в `outputs.tf` четыре выхода и замените `TODO`:

| Выход | Что должно получиться |
|---|---|
| `public_ips` | карта «имя → публичный IP» |
| `zones` | карта «имя → зона, которую выбрал модуль» |
| `urls` | список адресов страниц — из выхода `url` модуля |
| `servers_count` | сколько серверов (функция `length`) |

```bash
terraform plan      # Changes to Outputs — ресурсы не трогаются
terraform apply
terraform output    # zones = { "web-1" = "ru-moscow-1…" }, servers_count = 1 …
```

### Часть 5. terraform console: повторяем выбор зоны (10 мин)

`terraform console` — интерактивная проверка выражений на вашем настоящем state. Удобно, чтобы проверить `for` или функцию до того, как писать её в код.

```bash
terraform console
```

Попробуйте и объясните результат:

```hcl
keys(var.servers)
module.web["web-1"].zone
[for vm in module.web : vm.name]
md5("ivanov-petrov-web-1")
substr(md5("ivanov-petrov-web-1"), 0, 6)
parseint(substr(md5("ivanov-petrov-web-1"), 0, 6), 16)
```

**Задание:** повторите выбор зоны руками для **своего** имени ВМ (`<prefix>-web-1`). Список зон, где есть наш тип, модуль сортирует по алфавиту. Число из хэша возьмите по модулю числа таких зон (`%`) — получится номер зоны в этом списке, начиная с 0. Совпало с `module.web["web-1"].zone`?

Подсказка: все зоны региона — `data` внутри модуля, из console их не видно. Узнайте список у преподавателя или в консоли cloud.ru. Выход — `exit` или Ctrl+D.

> `console` читает state и ставит на него блокировку. Пока он открыт, `apply` в той же папке будет ждать — закрывайте его.

### Часть 6. Свой модуль firewall (20 мин)

Группа безопасности и два правила — тоже кандидат в модуль: в настоящем проекте таких групп несколько (для веб-серверов, для базы, для балансировщика). Заготовка — в папке `practice/firewall/`:

```bash
cat firewall/variables.tf     # входы готовы: name и ports — карта «порт => откуда»
grep -n TODO firewall/*.tf    # ресурсы и выход id — пишете вы
```

**1. Пишем модуль.** В `firewall/main.tf` — группа безопасности и правила через `for_each = var.ports`. В `firewall/outputs.tf` — выход `id`.

**2. Вызываем его** в `main.tf` вместо трёх ресурсов `sbercloud_networking_secgroup*` (их удалите):

```hcl
module "firewall" {
  source = "./firewall"                    # модуль может лежать и внутри папки проекта

  name = "${var.prefix}-web-sg"
  ports = {
    "22" = var.allowed_ssh_cidr
    "80" = "0.0.0.0/0"
  }
}
```

В вызове модуля `web`: `security_group_ids = [module.firewall.id]` — **выход одного модуля становится входом другого**.

```bash
terraform init      # новый модуль — снова init: "- firewall in firewall"
terraform plan
```

План хочет удалить старую группу и правила и создать новые. Пересоздание группы безопасности у работающей ВМ — это короткий обрыв SSH и HTTP.

**3. Бонус: переезд без пересоздания.** Раскомментируйте в конце `main.tf` первый блок `moved` (для группы) и допишите ещё два — для правил `ssh` и `http`. Цель:

```bash
terraform plan      # 0 to add, 0 to change, 0 to destroy — только "has moved to"
terraform apply
```

Адрес правила внутри модуля: `module.firewall.sbercloud_networking_secgroup_rule.this["22"]`.

<details><summary>Ответ: модуль firewall</summary>

```hcl
resource "sbercloud_networking_secgroup" "this" {
  name = var.name
}

resource "sbercloud_networking_secgroup_rule" "this" {
  for_each = var.ports

  security_group_id = sbercloud_networking_secgroup.this.id
  direction         = "ingress"
  ethertype         = "IPv4"
  protocol          = "tcp"
  port_range_min    = tonumber(each.key)
  port_range_max    = tonumber(each.key)
  remote_ip_prefix  = each.value
}

output "id" {
  value = sbercloud_networking_secgroup.this.id
}
```
</details>

## Если что-то не работает

| Симптом | Причина | Решение |
|---|---|---|
| `Unsupported Terraform Core version` | Terraform старше 1.6 | Поставить новую версию с зеркала (README занятия 10) |
| `Module not installed` | Добавили или изменили модуль без init | `terraform init` |
| `Unreadable module directory` / `source` не найден | Неверный путь в `source` | `"../modules/vm"` — путь от папки `practice`; `"./firewall"` — модуль внутри неё |
| `Invalid reference` в `subnet_id`/`key_pair` | Пропущена часть адреса | `data.<тип>.<имя>.id`, `<тип>.<имя>.name` |
| `Invalid value for variable` … `s7n.medium.2` | В вызове модуля задан другой `flavor` | Уберите `flavor` — модуль возьмёт минимальный |
| `Invalid value for variable` … `20 ГБ` | `disk_size` больше 20 | Уберите `disk_size` — модуль возьмёт минимум образа |
| `Квота: не больше одной ВМ на команду` | В `servers` больше одного сервера | Оставьте один `web-1` |
| `Тип ВМ s7n.medium.2 сейчас недоступен ни в одной зоне` | Тип распродан во всех зонах | Сообщите преподавателю |
| `Quota exceeded` / `Insufficient … quota` при apply | В проекте уже 15 ВМ (чьи-то не удалены) | Сообщите преподавателю; проверьте, что ваша ВМ из занятия 11 удалена |
| План хочет удалить web-1 после `for_each` | Сменился адрес ресурса | Блок `moved` из части 3 |
| `Unsupported attribute` … `zone` после `for_each` | Выходы части 1 ссылаются на `module.web.zone`, а это теперь карта | Закомментируйте их, напишите выходы части 4 |
| План хочет пересоздать группу безопасности в части 6 | Сменились адреса ресурсов | Блоки `moved` из бонуса части 6 |
| `plan` висит / `Error acquiring the state lock` | Открыт `terraform console` в другом окне | Закройте console (`exit`) |
