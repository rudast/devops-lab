# Занятие 12. Terraform в повседневной работе

Ничего принципиально нового: инфраструктура та же, что на занятии 11 — одна ВМ с приложением на команду. Сегодня мы учимся с ней **жить**: наводить порядок в коде, переименовывать ресурсы без пересоздания, замечать, когда облако разошлось с кодом, возвращать в state «потерянные» ресурсы, защищать важное от случайного удаления и включать-выключать ресурсы одной переменной.

Это приёмы, которые нужны каждую неделю в любой команде, где есть Terraform. Каждая часть — маленькое изменение и чтение плана.

### Часть 1. Порядок в коде (15 мин)

```bash
cd lesson12/practice
export SBC_ACCESS_KEY="…"  SBC_SECRET_KEY="…"
cp terraform.tfvars.example terraform.tfvars           # prefix команды
export TF_VAR_db_password="$(openssl rand -hex 12)"
terraform init
```

Код в папке специально слегка «помят». Две команды, которые в команде запускают перед каждым коммитом:

```bash
terraform fmt -check -diff      # какие файлы не по стандарту и что именно
terraform fmt                   # поправить. Ещё раз -check — тишина
terraform validate              # синтаксис и ссылки, без обращения к облаку
```

Теперь сломайте что-нибудь сами: в `main.tf` замените одно `var.prefix` на `var.prefx` и снова `validate`. Ошибка называет файл и строку — та же «Invalid reference», что на занятии 10, только теперь вы поймали её за секунду, не дожидаясь `plan`. Верните как было.

```bash
terraform plan        # Plan: 7 to add
terraform apply       # ВМ создаётся 1–2 минуты; приложение поднимется само за 3–7 минут — оно нам сегодня не главное
terraform output
```

> В настоящих проектах `fmt -check` и `validate` запускают автоматически при каждом pull request. Код, который не прошёл эти две проверки, в ревью не попадает.

### Часть 2. Переименовать ресурс, не пересоздавая (15 мин)

Сначала посмотрите на state глазами:

```bash
terraform state list                              # все ресурсы, которыми управляет Terraform
terraform state show sbercloud_kps_keypair.key    # один ресурс целиком: атрибуты из облака
```

Адрес ресурса — `тип.имя` — это ключ, по которому Terraform связывает код и облако. Переименуйте ресурс ключа в `main.tf`: `"key"` → `"ssh"` (и ссылку `sbercloud_kps_keypair.key.name` в ВМ тоже). Теперь:

```bash
terraform plan        # - sbercloud_kps_keypair.key   + sbercloud_kps_keypair.ssh   → 1 to add, 1 to destroy
```

Terraform не знает, что это тот же ключ: по его мнению, один ресурс исчез, другой появился. `apply` тут ещё и упал бы — ключ с таким именем в облаке уже есть. Вместо этого переносим запись в state:

```bash
terraform state mv sbercloud_kps_keypair.key sbercloud_kps_keypair.ssh
terraform plan        # No changes
```

Тот же переезд можно описать **в коде** блоком `moved` (раскомментируйте в конце `main.tf`, `plan` → «has moved to», `apply`, удалите блок). Разница: `state mv` — команда на одном ноутбуке, `moved` — изменение в Git, которое увидят в ревью и которое выполнится у всех.

> **Главное правило занятия:** если план после *переименования* хочет что-то удалить и создать заново — остановитесь. Это почти всегда переезд, а не изменение.

### Часть 3. Дрейф: облако разошлось с кодом (15 мин)

В веб-консоли cloud.ru найдите **свою** ВМ и поменяйте ей тег `lesson` с `12` на `manual` (или добавьте новый тег `drift = yes`). Это и есть дрейф: кто-то поправил руками то, что описано кодом.

```bash
terraform plan -refresh-only     # «Objects have changed outside of Terraform»: показывает, ЧТО изменилось в облаке
terraform plan                   # ~ tags: Terraform хочет вернуть как в коде
```

Два пути, и оба бывают правильными:

- **Код прав** — `terraform apply`: тег вернётся. Так чинят случайные правки.
- **Облако право** — `terraform apply -refresh-only`: state обновится под реальность, код не меняется. Но следующий `plan` снова покажет разницу: чтобы изменение осталось, его нужно внести **в код**.

Сделайте первый путь — верните как в коде. Обсудите в паре: когда бывает нужен второй?

> Дрейф — главная причина, почему в командах запрещают править инфраструктуру руками: следующий `apply` молча откатит чужую «быструю починку». На занятии 11 вы видели обратную сторону: то, что живёт внутри ВМ, Terraform не видит вовсе.

### Часть 4. Потерянный ресурс: `state rm` и `import` (15 мин)

Ситуация: ресурс в облаке есть, а в state его нет. Так бывает после отката state из бэкапа, после неудачного `state mv` или когда ресурс создали руками «на минутку». Устроим это сами:

```bash
terraform state rm sbercloud_kps_keypair.ssh     # убрали ТОЛЬКО запись из state, ключ в облаке остался
terraform plan                                    # Plan: 1 to add — хочет создать ключ заново
```

`apply` сейчас упадёт: ключ с таким именем в облаке уже есть. Правильный путь — **импорт**. Раскомментируйте в конце `main.tf` блок `import` и проверьте в нём адрес и `id` (у ключа ID — его имя):

```bash
terraform plan        # Plan: 1 to import, 0 to add, 0 to change, 0 to destroy
terraform apply
terraform plan        # No changes
```

Удалите блок `import`: он нужен один раз. Если после импорта `plan` показывает изменения — код описывает ресурс не так, как он есть в облаке. Это и есть смысл импорта: подогнать код под реальность, пока план не станет пустым.

> `import` — ещё и способ взять под управление Terraform то, что когда-то накликали в консоли. Для ВМ или сети `id` берут из консоли (это UUID), для ключа — имя.

### Часть 5. `lifecycle`: защитить важное (15 мин)

**1. Защита от удаления.** Публичный IP — ценный ресурс: он прописан в DNS, его знают пользователи. Добавьте в `sbercloud_vpc_eip.ip` блок:

```hcl
lifecycle {
  prevent_destroy = true
}
```

Проверьте, что защита работает — попробуйте удалить **только** IP флагом `-target`:

```bash
terraform destroy -target=sbercloud_vpc_eip.ip
#   Error: Instance cannot be destroyed … has lifecycle.prevent_destroy set
```

Запомните два приёма сразу: `-target` ограничивает команду одним ресурсом (аварийный инструмент, в обычной работе не нужен), а `prevent_destroy` превращает случайное удаление в ошибку.

**2. Порядок пересоздания.** В `terraform.tfvars` ограничьте SSH своим адресом: `allowed_ssh_cidr = "<ваш IP>/32"` (`curl -s ifconfig.me`). Правило группы безопасности нельзя изменить, только пересоздать — вы видели это на занятии 10:

```bash
terraform plan        # -/+ sbercloud_networking_secgroup_rule.ssh — сначала удалить, потом создать
```

Между «удалить» и «создать» SSH закрыт. Добавьте в правило `ssh`:

```hcl
lifecycle {
  create_before_destroy = true
}
```

```bash
terraform plan        # +/- — сначала создать новое, потом удалить старое
terraform apply
ssh root@$(terraform output -raw public_ip) hostname     # работает, разрыва не было
```

> Третий параметр `lifecycle` — `ignore_changes` — уже стоит у ВМ с занятия 11 (зона и образ). Теперь вы знаете все три.

### Часть 6. Выключатель публичного IP: `count` (10 мин)

Переменная `public_ip` уже есть в `variables.tf`. Сделайте так, чтобы при `public_ip = false` публичный IP и его привязка не создавались:

1. В `sbercloud_vpc_eip.ip` и `sbercloud_compute_eip_associate.ip_to_vm` добавьте `count = var.public_ip ? 1 : 0`.
2. Ссылка на адрес становится `sbercloud_vpc_eip.ip[0].address`: у ресурса с `count` всегда есть индекс.
3. В `outputs.tf` замените `local.eip` на `one(sbercloud_vpc_eip.ip[*].address)` — «ноль или один элемент»: адрес или `null`.

```bash
terraform plan        # No changes: count = 1 — ничего не изменилось
```

Теперь `public_ip = false` в `terraform.tfvars` и `terraform plan`:

```
Error: Instance cannot be destroyed
```

Сработала защита из части 5 — и это правильно: выключатель хочет удалить защищённый IP. Осознанно уберите `prevent_destroy`, снова `plan` (`- IP, - привязка`) и `apply`. `terraform output` покажет `public_ip = null`, `url = null` — выходы не падают благодаря `one()`. Верните `public_ip = true`, `apply` — IP вернулся (новый адрес: старый уже отдан облаку).

> `count = условие ? 1 : 0` — стандартный способ сделать ресурс «по условию». Для списков похожих ресурсов есть `for_each`, но это уже другая история.

### Часть 7. Уборка — и почему не с первого раза (5 мин)

```bash
terraform destroy
```

Если вернули `prevent_destroy` — `destroy` упадёт на IP. Так и задумано: защищённый ресурс удаляют осознанно, убрав защиту в коде. Уберите, снова `destroy`, и `terraform state list` → пусто.

## Если что-то не работает

| Симптом | Причина | Решение |
|---|---|---|
| `terraform fmt -check` молчит, а код «помятый» | Уже отформатирован (кто-то запустил `fmt`) | Так и должно быть после `fmt` |
| `Unsupported block type: import` | Terraform старше 1.5 | Новая версия с зеркала (README занятия 10) |
| `state mv`: `Resource already managed` | Ресурс с новым именем уже в state | `terraform state list` — проверьте, не сделали ли `mv` дважды |
| После `state mv` план не пустой | Не исправили ссылку `key_pair` в ВМ | `sbercloud_kps_keypair.ssh.name` |
| `plan -refresh-only` ничего не показывает | Тег не сохранился в консоли или другая ВМ | Проверьте имя ВМ: `<prefix>-app` |
| `Cannot import non-existent remote object` | Неверный `id` в `import` | ID ключа — его имя: `<prefix>-l12-key` |
| `apply` после `state rm`: ключ уже существует | Пропустили импорт | Блок `import` из части 4 |
| `Instance cannot be destroyed` | `prevent_destroy` | Так задумано: уберите строку осознанно |
| `Missing resource instance key` | После `count` ссылка без `[0]` | `sbercloud_vpc_eip.ip[0].address` |
| `Quota exceeded` при apply | Кончились vCPU/ВМ в проекте — чьи-то ВМ не удалены | Сообщите преподавателю; проверьте, что ВМ занятия 11 удалена |

## ⛔ Главное правило: ресурсы не оставляем

```bash
terraform destroy          # уберите prevent_destroy, если вернули его
terraform state list       # пусто
```
